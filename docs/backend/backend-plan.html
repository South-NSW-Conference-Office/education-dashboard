SNSW Adventist Education · Dashboards · Backend plan · September 2026

One spine for every number: unit → period → version → account → amount

The backend that replaces browser storage. It stores the operating statement at line-item grain, calculates every card on the server, and never lets a derived figure be typed. Proposed, not built.

Store source facts at the lowest trustworthy grain. Calculate everything else. Only raw-data endpoints accept writes. Every dashboard endpoint is read-only and computed. Approved report versions are immutable; a revised report is a new version.
Mechanism

MVC with a service layer: two paths through the stack

A read asks a controller for a computed view; a write lands on a draft version's line items. Both go through the same services, so the maths lives in one place and is unit-tested against the four existing boards.

Sequence

One edit, four screens: how a line item propagates

The finance officer changes one tuition line on Border Christian College. Nothing else is typed; the summary and the databoard move because they are computed from the same facts on the next read.

Entity model · finance core

Facts, the structures that give them meaning, and the checks around them

A fact is one amount at (version, unit, period, account, scenario, basis). Reporting groups and metric definitions are effective-dated so last year's report does not change when a mapping changes this year.

Entity model · weekly databoard and access

Only the judgement fields are stored

Four lights per school are opinions and are stored. Finance and Overall lights, the operating result and each school's budget and variance are read from the finance side at request time.

Contract

What accepts a write, what only shows a result

Writes (raw data)

  • line items on a DRAFT report version (values, codes, names, add, remove)
  • loans and leases, family debtor snapshot, period label
  • commentary notes and accountant queries
  • databoard: cash, loans and reserves tiles; building, staffing, enrolment details; the four judgement lights and cell notes; risks, WHS items, wins
  • admin, versioned: account mappings, metric definitions

Read-only (computed)

  • Overview KPIs, category totals, charts, going well / needs attention
  • salary sub-line, EBIDA add-back, operating margin
  • all-schools summary and consolidated totals
  • reconciliation checks and their status
  • databoard: operating result, school budget and variance, Finance light, Overall light

Order of work

Build so that step two reproduces today's dashboard exactly

  1. Schema, migrations, seed: four units, FY2026, the chart of accounts and groups taken from the four boards, metric definitions for EBIDA and salaries.
  2. Loader that imports the existing app/data/finance-*.js files as version 1 APPROVED per unit. The acceptance test is that every number on every screen matches the current frontend to the dollar.
  3. Services with unit tests against those four boards: roll-up, variance, EBIDA, salary sub-line, reconciliation, consolidation, status.
  4. Read endpoints and presenters; then write endpoints and workflow; then auth, per-unit access and audit.
  5. Frontend wiring: replace SNSW.store.load / save with the API client. The views do not change.
  6. Phase 2: MYOB, Synergetic and Hubworks sync jobs on the same import tables; amortisation rules as metric definitions once the finance team specifies them.
